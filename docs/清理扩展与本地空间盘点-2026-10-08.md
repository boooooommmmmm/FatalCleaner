## 2. 先处理一个已有范围问题

`fingerprints/fingerprints.json` 的 JetBrains 指纹把 `%LocalAppData%\\JetBrains` 整体列为 cachePaths，标有 devCache；`DevCacheScanner` 枚举此路径后统一赋予 Safe 风险级别。JetBrains 官方明确其 IDE system directory 同时包含缓存和 Local History，因此整个目录不能仅当作可再生成缓存。[JetBrains 目录说明](https://www.jetbrains.com/help/idea/directories-used-by-the-ide-to-store-settings-caches-plugins-and-logs.html)

建议优先缩小为具体 IDE 版本内已确认的缓存/日志子目录，明确保护 Local History；同时复核开发者扫描器和规则扫描器对同一缓存的风险评级。此处是静态代码与文档比对发现，本轮未实际执行该条清理，也未修改规则。首页一键优化有独立固定范围，不会因为这里标为 Safe 自动纳入 JetBrains。

## 3. 新增功能优先级

| 优先级 | 功能 | 当前缺口与建议首版 |
| --- | --- | --- |
| P1 | 项目构建产物清理 | 当前已有闲置 node_modules，但没有通用构建输出识别。先做用户指定根目录内的 .NET bin/obj；结合项目结构、生成文件清单及活动进程复核，预览后确认，不按文件夹名全盘删除。随后再研究 Rust target、前端工具缓存 |
| P1 | FatalCleaner 自身缓存管理 | 已有更新成功后的阶段目录/下载包清理；可补充失效待更新记录、不再适用的旧 ZIP、崩溃留下的部分下载，以及可配置的旧操作日志保留。保护正在下载/待安装的包与所有恢复记录，不把整个数据目录作为垃圾 |
| P1 | 常用办公应用缓存覆盖 | 飞书、钉钉、企业微信、腾讯会议、WPS 等可作为调查对象，先核实安装版本及实际缓存位置。首版只覆盖确定的缓存/旧日志，保留聊天附件、离线文件、会议录制、文档恢复和登录数据 |
| P2 | 卸载残留归属增强 | 已有僵尸目录首版限定当前用户 AppData，并需要卸载记录。结合安装快照、应用别名和占用检测，提高确认率；ProgramData 或原安装目录只按明确应用归属处理，共享组件保留 |
| P2 | 包管理器原生清理 | 从直接按固定路径删除升级为“检测工具 → 获取实际缓存位置 → 选择清理范围 → 调用官方维护能力”。避免自定义缓存路径漏扫，处理缓存锁和活动还原；全局依赖清理默认确认 |
| P2 | Docker 构建缓存清理 | 增加工具检测和空间报告，先做构建缓存；镜像单独预览，默认保留容器和卷，不直接删除 WSL 虚拟磁盘 |
| P3 | 失效下载任务 / 旧安装包整理 | 通过下载器记录、任务状态与文件归属判断；文件年龄只作为线索。未完成文件可能是用户仍想恢复的下载，默认不勾选 |

NuGet 官方提供缓存维护入口，并提示包还原并发锁；清空全局包会影响后续还原，不能等同于无代价优化。[NuGet 官方说明](https://learn.microsoft.com/en-us/nuget/consume-packages/managing-the-global-packages-and-cache-folders)

Docker 官方区分磁盘使用统计与 prune；只清构建缓存可以使用专用维护能力，避免宽范围 system prune 带来的对象删除。[Docker 空间统计](https://docs.docker.com/reference/cli/docker/system/)、[Docker 清理范围](https://docs.docker.com/reference/cli/docker/system/prune/)

这些是待开发建议，不是本轮新增的清理能力；新增应用路径要经样例/反例测试并签名后才启用。

## 5. 推荐顺序

1. 先收紧已有开发者缓存范围，避免将历史记录当缓存。
2. 首个新增模块选“项目构建产物清理”，本机已有明确需求和测试样本。
3. 同期做本程序旧更新包管理，再扩常用办公应用和卸载缓存覆盖。
4. 本地整理先处理约 685.7 MiB 的旧预览/发布副本；构建缓存和验收二进制按需处理，保留证据。

本轮没有执行删除、改动清理规则或发布。扫描明细在 `artifacts/verification/cleanup-analysis-2026-10-08/sizes.json` 和 `verification-sizes.json`。
