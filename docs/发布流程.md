# FatalCleaner 发布流程

维护日期：2026-10-07。用于发布新版本；现有版本的结果见[文档索引](README.md)中的发布记录。版本号、构建提交与 CI 结果以本次实际状态为准。

## 1. 准备源码

1. 核对工作区、远端 `boooooommmmmm/FatalCleaner`、分支和已有版本；使用新版本号，不覆盖已公开的同版本资产。
2. 同步 App、Service 的 `.csproj` 版本及 `src/CleanSweep.App/app.manifest`，编写 `docs/releases/发布说明-v<版本>.md`。
3. 提交并推送本次源码、测试和说明。构建前后运行 `tools/verify-release-source.ps1`，确认 HEAD 一致。该脚本拒绝未跟踪及未提交改动，仅允许本次生成的 `release/latest.json`。
4. 使用干净的 `publish/<RID>` 和 `publish/portable-<RID>` 输出目录。`tools/publish.ps1` 拒绝非空或相互嵌套目录；移开旧目录前核对绝对路径，保留历史包。

## 2. 打包与验证

下例中的 `<版本>` 和 `<本轮说明>` 需要替换。先打包，再按后续步骤公开附件：

```powershell
./tools/verify-release-source.ps1
./tools/release.ps1 -Repo boooooommmmmm/FatalCleaner -Version <版本> -Notes <本轮说明>
./tools/verify-release-source.ps1
./tools/verify.ps1 -Configuration Release -PackageDir publish/win-x64 -ReleaseZip publish/FatalCleaner-win-x64-<版本>.zip -ResultsDirectory artifacts/verification/release-v<版本>
```

版本必须与二进制一致。发布目录包含 App、Service、运行时、签名数据集和 `install-files.txt`。最终源码提交的 `.github/workflows/verify.yml` Debug / Release 检查通过后再公开。

同时生成 `publish/portable-<RID>/FatalCleaner.exe`，作为单文件免安装附件。兼容目录的 `CleanSweep.exe` 与它字节相同，仍需保留外置规则和服务运行时。`release/latest.json` 必须继续指向兼容 ZIP，供新旧客户端统一验签下载；不能改成 EXE 地址。旧用户继续保留原路径与服务，单文件入口更新只替换自己。详见[兼容方案及验收](单文件免安装与升级兼容-2026-10-07.md)。

发布脚本在相同体系结构上自动运行 `tools/verify-portable.ps1`，只校验内置数据、SQLite 和图标，不运行主界面或清理。跨架构发布须在目标机器运行同一自检。涉及更新协议改动时，再用 `tools/CleanSweep.PackageCheck` 与保留的旧正式包进行兼容检查。

`tools/release.ps1` 的 `-Publish` 会直接创建正式 Release 再上传附件；默认打包模式的控制台提示也仍把清单推送放在附件发布之前。本流程采用草稿上传与验证顺序，执行时以本流程为准。签名私钥和发布令牌由仓库外提供，公开验证只使用公钥。

## 3. 发布附件

1. 创建指向已推送构建提交的草稿 Release，上传签名清单对应的 ZIP 和单文件 `FatalCleaner.exe`，核对两个附件的服务端大小与 digest。EXE 附件必须保留该文件名。
2. 从草稿转为正式发布时，明确指定正式 `tag_name` 和 `draft: false`；需要设为最新版时指定 `make_latest: "true"`，防止遗留 `untagged-*` 资产地址。
3. 核对 tag 的实际提交、Release 状态、附件 URL 与签名清单。
4. 从正式附件地址匿名下载两个附件，验证大小和 SHA-256，ZIP 额外验证发布签名。下载到独立目录并保留正式 ZIP 文件名，`verify-release` 会检查文件名；确认独立 EXE 的 SHA-256 与 ZIP 中 `CleanSweep.exe` 一致，并运行自检。

```powershell
dotnet run --project tools/CleanSweep.SignData -c Release -- verify-release release/latest.json <独立目录>/FatalCleaner-win-x64-<版本>.zip
```

若构建提交改变，重新打包、签名、验证，并在核对本轮草稿及资产身份后替换未公开附件。已公开版本不使用这一替换流程。

## 4. 推送更新清单并核对入口

公开附件验证通过后，才提交并推送 `release/latest.json` 和发布验收记录，避免客户端先看到新版本却无法下载。

分别核对：

- GitHub 正式 Release 与公开附件。
- 仓库中的新清单。
- 客户端实际使用的 `https://raw.githubusercontent.com/boooooommmmmm/FatalCleaner/main/release/latest.json`。

raw 缓存曾延迟约 5 分钟；仓库 API 已更新不表示客户端入口立即更新。等待实际地址返回新清单，再验证签名及资产匹配。若超过几轮缓存周期仍不一致，记录并调查，不反复重发附件。GitHub 来源另有 jsDelivr 网络故障回退，签名规则相同。

## 5. 收尾

将 Release URL、tag SHA、资产大小 / 哈希、源码 CI、测试结果及验收边界写入 `docs/releases/发布验收-v<版本>.md`，更新[当前状态](当前状态.md)与文档索引。核对工作区和远端状态。

真实 UAC、SYSTEM 服务、安装回滚与断电恢复未测试时，明确记录。生成 JSON 如需从 CRLF 转为 LF，转换后复验签名，不修改签名字段。
