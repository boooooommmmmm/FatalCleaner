# NuGet 依赖误清理事故与防护

记录日期：2026-10-08。严重性：高；实际造成开发构建中断。防护已在 **v0.25.0 正式发布**，见[发布验收](releases/发布验收-v0.25.0.md)。升级前运行的旧版仍需暂停相关清理；下文恢复过程按当时状态记录。

## 已确认事实

用户执行 Unity 工程 `./jam -j=128 WebGLPlayerNoDevelopment`，构建 Unity.BuildSystem 时出现 160 条 CS0006。缺失路径均位于用户的 `.nuget/packages/microsoft.netcore.app.ref/6.0.13/ref/net6.0/`。

只读查询本机 `AppData/Local/CleanSweep/cleansweep.db`，160 个报错路径全部匹配隔离记录，全部有永久删除记录。该包版本共 293 个文件被 `dev-cache` 移入隔离区；批次 `20261007-033655-02e46b`，北京时间 2026-10-07 11:38:34–35。样例 System.Runtime.dll 于 12:02:00 被永久删除，隔离路径随后不存在。未发现恢复记录。

这些记录证明构建依赖由清理模块移走后永久删除；尚不能确认永久删除由用户操作还是自动维护触发。PowerShell 更新通知与此无关。

## 根因与审查遗漏

1. 指纹库把 `.nuget/packages` 作为开发缓存；DevCacheScanner 对指纹缓存统一赋予 Safe，因此默认勾选。
2. 同一路径在 dev.json 中为 Confirm；两个扫描入口风险不一致。
3. 将“可以重新下载”误当成“不影响使用”。NuGet 全局目录是项目当前引用程序集的位置，自定义增量构建未必先还原。
4. 底层路径护栏未保护依赖仓库，其他扫描入口也可能提交这些文件。
5. 此前测试和审查未覆盖“扫描与执行保护真实依赖、旧选择、隔离维护”的完整过程；原有开发者测试甚至断言 Gradle 依赖缓存应为 Safe。该断言已纠正。

## 已实现防护

- **路径保护**：目标用户默认路径下的 NuGet、Maven、Gradle 依赖/发行版、Cargo 源码/仓库、Go 模块、Dart pub、Bun 依赖、pnpm store、Deno 模块、Conda 环境/包、Poetry 虚拟环境、uv 缓存，以及已知工具链与浏览器运行包等不能作为清理目标；清理其父目录也拒绝。
- **执行再次校验**：扫描、CleanEngine 逐文件/整目录处理以及有护栏的 Quarantine.MoveIn 均受保护。旧扫描结果即使标为 Safe，或改从应用缓存、重复文件、残留入口提交，也不能清理已保护路径。
- **自定义环境变量**：当前用户环境解析器收集 NUGET_PACKAGES、GRADLE_USER_HOME、CARGO_HOME、RUSTUP_HOME、GOPATH/GOMODCACHE、PUB_CACHE、DENO_DIR、PNPM_HOME、UV_CACHE_DIR、CONDA_PKGS_DIRS/CONDA_PREFIX，作为额外保护范围。它们不能授权清理。
- **未知开发缓存保守处理**：指纹开发缓存默认 Confirm；category=dev 的规则至少为 Confirm，不再仅依赖在线数据的 Safe 标记。应用页和开发者页均如此，已有更高风险保持不变。
- **每次重新选择**：开发缓存不恢复上次勾选。规则条目保留显式 RequiresFreshSelection 标记，不要求规则 ID 必须以 dev. 开头。旧 Safe 开发缓存执行请求要求重新扫描。
- **保留恢复机会**：旧 dev-cache 隔离项及当前护栏识别的依赖隔离项，不再由到期或容量淘汰自动永久删除。显式手动删除仍有效；隔离区说明同步更新。保护清理不会阻止把旧依赖恢复到原位置。
- **兼容旧数据**：旧签名规则和指纹仍可解析，由运行期策略拒绝危险目标，避免整条 NuGet 规则被拒绝后连 HTTP 缓存的安全检查也丢失。内置签名数据未因此改写。

## 本次依赖恢复

用户再次报告 DLL 缺失后，已实际执行工程自带 SDK 的还原命令：

```powershell
Set-Location C:\workspace\tj_trunk
& '.\artifacts\Stevedore\dotnet-sdk-win-x64_031d\dotnet.exe' restore `
    '.\Tools\Unity.BuildSystem\Unity.BuildSystem.gen.csproj' `
    --force --no-cache --packages 'C:\Users\shuyan.hu\.nuget\packages'
```

SDK 7.0.102，命令退出码 0，输出 Restored。逐一核对原始日志的 160 个缺失路径：**160 个均已存在，剩余缺失 0 个**。包括用户后续提供的 System.Web.HttpUtility.dll、System.Xml.*.dll、WindowsBase.dll。未执行完整 Unity WebGL 构建；后续编译阶段是否仍缺其他依赖，需要以该工程重编译结果为准。没有清空全局包缓存或删除 Unity artifacts。

## 验证与边界

### 后续 CS2001 与批量依赖恢复

用户随后报告 `microsoft.net.test.sdk/16.5.0/build/netcoreapp2.1/Microsoft.NET.Test.Sdk.Program.cs` 缺失（CS2001）。只读查库确认该文件同属批次 `20261007-033655-02e46b`：北京时间 2026-10-07 11:38:37 隔离、12:01:59 永久删除。不是项目源码被本轮恢复操作移除，而是同一批清理影响了测试 SDK。

前次还原仅覆盖 Unity.BuildSystem 主项目，未覆盖测试项目及其他工具。本次先使用工程 SDK 7.0.102 对 `Tools/Unity.BuildSystem/Unity.BuildSystem.gen.sln` 执行 `restore --force --no-cache --packages`，主项目、测试项目、Bee BuildProgram 三个项目还原成功；报错的 Program.cs 确认存在。

随后扫描该 Unity 工程现有 **240 份 project.assets.json、3,337 份编译响应文件**（排除 Stevedore 工具分发目录与 .git）。把其中引用的缺失 NuGet 文件与真实清理记录交叉匹配，识别出 **122 个缺失包版本、4,954 个缺失引用文件**。

在 FatalCleaner 忽略的 artifacts/verification 目录生成独立 PackageDownload 恢复项目，逐包指定原始精确版本，使用与原工程相同的华为云 NuGet 镜像，经 NuGet 正常安装流程补回用户全局包目录；没有给 Unity 项目添加/升级 PackageReference，也没有删除 artifacts 或清空缓存。所有清单内文件复查存在：**4,954 / 4,954，剩余 0**。测试 SDK 16.5.0 的报错源码也复查存在。证据：`unity-dependency-audit.json`、`RestoreAffectedPackages.csproj`、`unity-dependency-recovery.json`，均位于 `artifacts/verification/developer-cache-safety-2026-10-08/`。

以上覆盖现有清单可见、且匹配清理记录的引用；尚未执行完整 Unity WebGL 构建，不代表所有平台、后续生成的清单或私有依赖均已验证。此次为依赖恢复及文档更新，未改变上轮防护源码，测试基线仍为 767 项通过。

使用隔离临时目录、内存数据库测试；未用真实用户文件测试清理。验证入口与结果见 `artifacts/verification/developer-cache-safety-2026-10-08/full/`；恢复路径核对见同目录上级的 `dependency-restore.json`。

本轮覆盖依赖根/子路径/父路径、恢复路径、相似目录名、额外环境变量、旧指纹/规则、未知开发缓存、跨模块提交、旧勾选、自动淘汰与恢复。完整测试数量及状态见[当前状态](当前状态.md)。

保护范围不是任意目录中的所有开发依赖：尚未读取每个工具的项目级/用户级配置来发现任意自定义仓库，也不保证自动识别所有第三方工具。SYSTEM 为其他用户执行时，不能凭服务自身环境推断目标用户的自定义依赖变量。真实多用户/UAC/SYSTEM 场景仍需专门验收。普通项目 node_modules 清理继续要求手动确认，不应描述为零风险。

在修复版本正式发布并替换运行中的旧程序前，本地源码防护不会自动作用于旧 EXE。此次依赖恢复也不会使旧版本获得新保护。

## 后续规则准入要求

新增清理范围需说明是否被构建/运行直接引用，是否含本地发布包、唯一副本、配置或离线依赖；仅凭目录名含 cache 或可以下载，不能判为 Safe。新增依赖相关范围必须覆盖默认选择、其他入口、旧数据与执行护栏，并验证隔离恢复。无法证实可安全删除时，保留原文件。
